# AC Verifier 스킬

GitHub Issue의 AC를 **브라우저에서 실제 앱을 조작**하여 검증한다.
단위 테스트가 아닌, 사용자가 실제로 앱을 사용하는 관점에서 확인하는 것이 목적이다.

## 입력

`$ARGUMENTS` = GitHub 이슈 번호 (예: `3`)

## 왜 브라우저 검증인가

단위 테스트는 코드 단위의 동작을 검증하지만, 실제 브라우저에서의 동작은 다를 수 있다.
CSS 렌더링, 이벤트 전파, API 연동, 사용자 인터랙션 등은 브라우저에서만 확인 가능하다.
AC는 "사용자가 이것을 할 수 있다"를 정의하므로 사용자 관점의 검증이 필요하다.

---

## 실행 순서

### Step 1. AC 목록 로드

```bash
gh issue view $ARGUMENTS
```

AC 체크리스트(`- [ ]` 항목)를 추출하여 검증할 목록을 만든다.
issues.md Gherkin 시나리오도 참고한다.

### Step 2. 앱 실행 확인

앱이 실행 중인지 확인한다:

- http://localhost:5173 (프론트엔드)
- http://localhost:3001/notes (API)

실행 중이 아니면 개발자에게 `npm run dev` 실행을 요청한다.

### Step 3. 브라우저 탭 준비

chrome 브라우저 도구를 사용하여:

1. `tabs_context_mcp`로 현재 탭 상태를 확인한다
2. 새 탭을 생성하고 `http://localhost:5173`으로 이동한다

### Step 4. AC별 검증 루프

각 AC 항목에 대해 다음을 수행한다:

#### 4-1. 검증 계획 수립

AC 항목을 읽고, 이를 검증하기 위한 구체적인 브라우저 조작 단계를 계획한다.

예시:

```
AC: "노트 편집 시 태그를 추가할 수 있다"
→ 1. 노트 목록에서 노트 클릭
→ 2. 태그 입력 필드에 "react" 입력
→ 3. Enter 키 누르기
→ 4. "react" 칩이 나타나는지 확인
→ 5. 스크린샷 촬영
```

#### 4-2. 브라우저 조작

chrome 도구를 사용하여 계획한 단계를 실행한다:

- `navigate` — 페이지 이동
- `read_page` — 현재 상태 확인 (Live 모드 권장)
- `form_input` — 입력 필드에 텍스트 입력
- `computer` — 클릭, 키보드 입력 등
- `javascript_tool` — DOM 상태 직접 확인이 필요할 때

#### 4-3. 스크린샷 촬영

각 AC 검증 후 `computer` 도구의 screenshot 기능으로 현재 화면을 캡처한다.
스크린샷을 확인하여 시각적으로도 정상인지 판단한다.

#### 4-4. 결과 기록

AC별로 PASS/FAIL을 판정한다:

- **PASS**: 기대한 대로 동작함
- **FAIL**: 기대와 다르게 동작함 — 구체적인 차이를 기술

### Step 5. API 상태 확인

데이터가 실제로 저장/변경되었는지 API를 통해 확인한다:

```
javascript_tool로 fetch('http://localhost:3001/notes') 실행
```

### Step 6. 결과 요약 및 보고

검증 결과를 개발자에게 보고한다:

```
## AC 검증 완료 — Issue #{N}: {제목}

| # | AC | 결과 | 비고 |
|---|-----|:----:|------|
| 1 | AC 내용 | PASS | 정상 동작 |
| 2 | AC 내용 | FAIL | 기대: X, 실제: Y |

### PASS: N개 / FAIL: N개

### FAIL 상세 (해당 시)
- AC #2: 구체적인 실패 내용과 재현 단계
```

### Step 7. GitHub Issue 업데이트

모든 AC가 PASS인 경우:

- 개발자에게 이슈 닫기를 제안한다
- `gh issue close $ARGUMENTS`는 개발자 승인 후 실행

FAIL이 있는 경우:

- 실패 항목을 개발자에게 보고하고 수정 방향을 제안한다
- 이슈는 열어둔다

---

## 검증 팁

- **초기 상태부터 시작**: 매 AC 검증 전 페이지를 새로고침하여 깨끗한 상태에서 시작
- **데이터 확인**: UI 표시뿐 아니라 실제 데이터가 저장되었는지 API로 확인
- **에지 케이스**: AC의 Gherkin 시나리오에 명시된 경계 케이스도 브라우저에서 검증
- **스크린샷 활용**: 시각적 요소(칩 렌더링, 레이아웃 등)는 반드시 스크린샷으로 확인

## 절대 금지

- 코드를 수정하는 것 — 검증만 수행한다
- AC에 없는 항목을 검증하는 것
- 검증 없이 PASS로 판정하는 것
