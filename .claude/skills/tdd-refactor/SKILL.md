# TDD Refactor 스킬

테스트 통과 상태를 유지하면서 **코드 구조를 개선**한다.
Green 단계에서 "일단 동작하게" 만든 코드를 "잘 동작하게" 다듬는 것이 목적이다.

## 입력

`$ARGUMENTS` = issues.md 내부 이슈 번호 (예: `1`)

## 핵심 원칙

Refactor 단계에서는 외부 동작(테스트)을 바꾸지 않고 내부 구조만 개선한다.
모든 변경 후 테스트가 통과해야 한다 — 테스트가 깨지면 변경을 되돌린다.

---

## 실행 순서

### Step 1. 프로젝트 컨벤션 파악

`CLAUDE.md`를 읽어서 프로젝트 컨벤션을 파악한다:

- 네이밍 패턴 (파일명, 컴포넌트, Props, API 함수, 이벤트 핸들러)
- 컴포넌트 구현 패턴 (named export, Props 인터페이스, 조건부 렌더링 순서)
- 상태 관리 패턴 (UI 상태 vs 도메인 상태 vs 폼 상태)
- API 호출 패턴 (에러 처리, 타입 어노테이션)
- 스타일링 컨벤션 (Tailwind 유틸리티, CSS 커스텀 속성)

### Step 2. 현재 테스트 상태 확인

```bash
npm test
```

전체 테스트가 통과하는지 확인한다. 실패 테스트가 있으면 리팩토링을 진행하지 않고 개발자에게 보고한다.

### Step 3. 리팩토링 대상 파일 식별

이번 이슈에서 변경된 파일만 리팩토링 대상으로 한다:

```bash
git diff main...HEAD --name-only -- src/
```

결과에서 테스트 파일(`*.test.ts`, `*.test.tsx`)을 제외한 파일이 리팩토링 대상이다.

각 파일을 아래 **점검 기준**으로 검토한다:

#### 점검 기준

| 항목                    | 질문                                              | 예시                                            |
| ----------------------- | ------------------------------------------------- | ----------------------------------------------- |
| 중복 제거               | 같은 로직이 반복되는가?                           | 동일한 폴백 패턴이 여러 곳에 있으면 함수로 추출 |
| 네이밍 명확성           | 변수/함수 이름이 의도를 드러내는가?               | `data` → `fetchedNotes`, `fn` → `handleTagAdd`  |
| 단일 책임               | 하나의 함수/컴포넌트가 너무 많은 일을 하는가?     | 200줄짜리 컴포넌트에 로직+스타일+데이터 혼재    |
| 불필요한 복잡도         | 매직 넘버, 과도한 중첩, 불필요한 추상화가 있는가? | 3단 이상 중첩 if, 의미 없는 래퍼 함수           |
| CLAUDE.md 컨벤션 불일치 | 프로젝트 패턴과 어긋나는 코드가 있는가?           | default export 사용 (패턴은 named export)       |

### Step 4. 리팩토링 계획 보고 및 승인

발견한 개선점을 개발자에게 보고하고 AskUserQuestion으로 승인을 받는다.

표시 형식:

```
## 리팩토링 대상 — Issue #{N}

### 파일: src/path/to/file.ts

| # | 항목 | 현재 | 개선안 |
|---|------|------|--------|
| 1 | 네이밍 | `data` | `fetchedNotes` |
| 2 | 중복 | 폴백 패턴 3회 반복 | 헬퍼 함수 추출 |
```

승인 시 진행, 수정 요청 시 계획을 조정한다.
개선점이 없으면 "리팩토링 불필요"를 보고하고 종료한다.

### Step 5. 하나씩 변경 → 테스트 → 확인

승인된 개선점을 **하나씩** 적용한다:

1. 하나의 개선점을 코드에 반영한다
2. 즉시 테스트를 실행한다:
   ```bash
   npm test
   ```
3. 결과를 확인한다:
   - **전체 통과**: 다음 개선점으로 이동
   - **테스트 실패**: 즉시 변경을 되돌리고 다른 접근을 시도한다

### Step 6. 테스트 실패 시 롤백

테스트가 깨지면:

1. 변경을 되돌린다 (git checkout 또는 수동 복원)
2. 실패 원인을 분석한다
3. 다른 접근 방식을 시도하거나, 해당 개선점을 건너뛴다
4. `npm test`로 롤백 후 전체 통과를 재확인한다

### Step 7. 결과 요약

모든 개선을 적용한 후 결과를 보고한다:

```
## TDD Refactor 완료 — Issue #{N}

### 변경 요약

| # | 파일 | 변경 내용 | 점검 항목 |
|---|------|----------|----------|
| 1 | src/path/to/file.ts | data → fetchedNotes | 네이밍 |
| 2 | src/context/Xxx.tsx | 폴백 패턴 함수 추출 | 중복 제거 |

### 테스트 결과
- 전체: N개
- 통과: N개 ✓
- 실패: 0개

### 건너뛴 항목 (해당 시)
- #3: 이유 설명
```

## 절대 금지

- **새 기능을 추가하는 것** — 외부 동작을 바꾸지 않는다
- **테스트 파일을 수정하는 것** — 테스트는 사양이다
- **src/ 디렉토리 밖을 수정하는 것** — 코드만 리팩토링한다
- **git diff 결과 밖의 파일을 수정하는 것** — 이번 이슈 범위만 다룬다
- **테스트가 깨진 채로 다음 변경으로 넘어가는 것** — 반드시 롤백 후 진행
