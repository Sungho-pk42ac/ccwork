# TDD Green 스킬

실패 중인 테스트를 통과시키는 **최소한의 구현 코드**만 작성한다.
TDD Red 단계에서 작성된 테스트를 Green으로 만드는 것이 목적이다.

## 입력

`$ARGUMENTS` = issues.md 내부 이슈 번호 (예: `1`)

## 핵심 원칙

Green 단계의 목표는 "테스트를 통과시키는 가장 단순한 코드"를 작성하는 것이다.
리팩토링, 최적화, 추가 기능은 이 단계에서 하지 않는다.
테스트가 요구하지 않는 코드는 작성하지 않는다 — 테스트가 사양서다.

---

## 실행 순서

### Step 1. 현재 실패 상태 확인

```bash
npm test
```

실패 테스트 목록과 에러 메시지를 파악한다. 어떤 테스트가 왜 실패하는지 이해한다.

### Step 2. Collect 실패 감지 및 Stub 생성

시나리오 문서와 vitest 출력을 비교하여 테스트가 제대로 수집되었는지 확인한다.

1. `docs/features/tag/issue-{$ARGUMENTS}.md`에서 테스트 시나리오 체크박스(`- [`)의 총 건수를 센다
2. Step 1의 vitest 출력에서 보고된 Tests 수를 확인한다
3. **건수 불일치 시**: import 대상 모듈이 존재하지 않아 vitest가 테스트를 수집하지 못한 것이다. 시그니처 문서에 명시된 경로에 **시그니처만 있는 stub 파일**을 생성한다.

Stub 파일 규칙:

- 함수: 시그니처만 export하고 body는 `throw new Error('Not implemented')` 또는 적절한 기본 반환값
- 타입/인터페이스: 시그니처 문서 그대로 작성
- 컴포넌트: 빈 JSX를 반환하는 최소 컴포넌트
- 훅: 기본값을 반환하는 최소 구현

Stub 생성 후 `npm test`를 다시 실행하여 전체 테스트가 수집되는지 확인한다.

### Step 3. 디자인 컨텍스트 로드

UI 컴포넌트를 구현해야 하는 이슈라면 디자인 정보를 먼저 파악한다.

1. `docs/design-system.md`가 존재하면 읽는다. 없으면 디자인 시스템 스킬이나 관련 문서를 찾는다.
2. `docs/features/tag/issue-{$ARGUMENTS}.md`에 "디자인 참고" 섹션이 있으면 확인한다
3. `CLAUDE.md`의 스타일링 컨벤션을 참조한다

디자인 문서가 없으면 이 단계를 건너뛰고 CLAUDE.md 컨벤션만 따른다.

### Step 4. 실패 테스트를 하나씩 통과시키기

첫 번째 실패 테스트부터 시작한다.

#### 구현 원칙

- **테스트가 요구하는 것만 구현한다.** 테스트가 검증하지 않는 코드는 작성하지 않는다.
- **기존 코드 패턴을 따른다.** CLAUDE.md에 명시된 패턴(named export, Props 인터페이스, 에러 처리 등)을 준수한다.
- **UI 컴포넌트**를 구현할 때는 테스트가 요구하는 동작을 충족하면서 디자인 문서의 Tailwind 클래스, 레이아웃, 상태별 표현을 적용한다. 디자인 문서에 없는 시각적 요소는 추가하지 않는다.
- **한 번에 하나의 테스트만 집중한다.** 여러 테스트를 한꺼번에 통과시키려 하지 않는다.

### Step 5. 테스트 실행 및 피드백 루프

구현 후 즉시 테스트를 실행한다:

```bash
npm test
```

결과를 확인한다:

- **해당 테스트 통과 + 회귀 없음**: Step 6으로 진행
- **해당 테스트 여전히 실패**: 에러 메시지를 분석하고 코드를 수정한 뒤 Step 5를 반복한다 (최대 5회)
- **5회 반복 후에도 실패**: 개발자에게 실패 원인과 시도한 접근 방식을 보고하고 중단한다
- **다른 테스트가 깨짐 (회귀)**: 회귀를 먼저 수정한다. 이번 변경이 원인이라면 접근을 재고한다.

### Step 6. 시나리오 문서 체크

통과한 테스트에 대응하는 `docs/features/tag/issue-{$ARGUMENTS}.md`의 시나리오 항목을 `[x]`로 체크한다.

예시:

```markdown
- [ ] normalizeTag — should return "react" when input is " React "
```

→

```markdown
- [x] normalizeTag — should return "react" when input is " React "
```

### Step 7. 다음 실패 테스트로 이동

남은 실패 테스트가 있으면 Step 4로 돌아간다.
모든 테스트가 통과하면 Step 8로 진행한다.

### Step 8. 커버리지 측정

전체 테스트가 통과한 후 커버리지를 측정한다:

```bash
npx vitest run --coverage
```

커버리지 결과를 확인하고:

- 이번 이슈에서 구현한 파일의 커버리지를 보고한다
- 미커버 라인이 있으면 시나리오에서 빠진 케이스인지 확인하여 개발자에게 알린다
- **커버리지를 올리기 위해 테스트를 추가하지 않는다** — 참고 정보로만 활용

### Step 9. 결과 요약

```
## TDD Green 완료 — Issue #{N}

### 구현한 파일
- src/path/to/file.ts — 변경 내용 요약

### 테스트 결과
- 전체: N개
- 통과: N개 ✓
- 실패: 0개

### 커버리지
- 파일별 라인 커버리지

### 미커버 라인 (참고)
- 해당 시 목록
```

---

## 절대 금지

- **테스트 파일을 수정하는 것** — 테스트는 Red 단계에서 확정된 사양이다
- **테스트에 없는 기능을 구현하는 것** — Green은 "테스트 통과"가 유일한 목표다
- **불필요한 추상화** — 헬퍼, 유틸, 래퍼를 테스트가 요구하지 않는 한 만들지 않는다
- **디자인 문서에 없는 시각적 요소를 추가하는 것** — 디자인은 명세를 따른다
- **커버리지를 위한 테스트 추가** — 커버리지는 참고용이다
