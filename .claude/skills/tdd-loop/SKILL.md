# TDD Loop 스킬

이슈 1개를 받아 **사전 점검 → test-scenarios → tdd-red → tdd-green → ac-verifier → tdd-refactor → security-review → create-pr** 순서로 TDD 풀 사이클을 진행한다.

이 스킬은 **컨테이너**다. 각 단계의 실제 로직은 기존 스킬/에이전트가 담당하며, 컨테이너는 순서 보장과 진행 상태 출력만 한다.

## 입력

`$ARGUMENTS` = GitHub 이슈 번호 (예: `5`)

## 핵심 규칙

- 각 스킬/에이전트 내부의 사용자 승인 게이트는 **그대로 작동**한다 (사용자가 응답해야 다음 진행)
- 컨테이너 자체는 **"다음 단계 진행할까요?" 같은 추가 게이트를 만들지 않는다**
- 단계가 성공적으로 끝나면 바로 다음 단계로 넘어간다
- **단계 실패 시** 어디서 멈췄는지 명확히 출력하고 **즉시 중단**한다

---

## 진행 상태 출력 형식

각 단계 시작 시 다음 형식으로 진행 상태를 출력한다:

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
[N/7] 단계 이름 — Issue #$ARGUMENTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

---

## Step 0. 사전 점검

스킬/에이전트를 호출하기 전에 작업 환경이 준비되었는지 확인한다. 하나라도 실패하면 사용자에게 알리고 중단한다.

### 0-1. 이슈 확인

```bash
gh issue view $ARGUMENTS
```

이슈 본문과 AC(Acceptance Criteria)를 읽어서 유효한 이슈인지 확인한다. 이슈가 없거나 닫혀 있으면 중단한다.

### 0-2. 작업 트리 클린 확인

```bash
git status --porcelain
```

출력이 있으면(uncommitted changes) 중단한다. 안전을 위해 깨끗한 상태에서만 시작한다.

### 0-3. 현재 브랜치 확인

```bash
git branch --show-current
```

현재 브랜치가 `feature/` 접두사를 가진 스펙 브랜치인지 확인한다 (예: `feature/tag-spec`). 스펙 브랜치가 아니면 중단하고 안내한다.

현재 브랜치 이름을 `$SPEC_BRANCH`로 기억해둔다 — Step 7에서 PR base로 사용한다.

### 0-4. 작업 브랜치 생성

이슈 제목에서 슬러그를 추출하여 `feat/issue-{N}-{slug}` 형태의 브랜치명을 만든다.

해당 브랜치가 **이미 존재**하면:

- 동일 이슈 재실행으로 간주하고 AskUserQuestion으로 사용자에게 확인한다
  - "기존 브랜치에서 이어서 작업" / "기존 브랜치 삭제 후 새로 시작" / "취소"
- 취소 선택 시 중단한다

브랜치가 **없으면**:

```bash
git checkout -b feat/issue-{N}-{slug}
```

### 0-5. 사전 점검 완료 출력

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
[0/7] 사전 점검 완료 — Issue #$ARGUMENTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
이슈: #{N} {제목}
스펙 브랜치: $SPEC_BRANCH
작업 브랜치: feat/issue-{N}-{slug}
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

---

## Step 1. 테스트 시나리오

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
[1/7] 테스트 시나리오 — Issue #$ARGUMENTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

`/test-scenarios $ARGUMENTS` 스킬을 호출한다.

이 스킬 내부에서:

- 시그니처 승인 게이트 (사용자가 확인)
- 시나리오 승인 게이트 (사용자가 확인)

가 작동한다. 사용자가 승인하면 다음 단계로 넘어간다.

---

## Step 2. TDD Red

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
[2/7] TDD Red — Issue #$ARGUMENTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

`/tdd-red $ARGUMENTS` 스킬을 호출한다.

시나리오를 실패하는 테스트 코드로 변환한다. collect 실패 시 스킬 내부에서 stub 생성을 안내한다.

---

## Step 3. TDD Green

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
[3/7] TDD Green — Issue #$ARGUMENTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

`/tdd-green $ARGUMENTS` 스킬을 호출한다.

최소 구현으로 테스트를 통과시킨다. 내부에서 최대 5회 피드백 루프가 돌고, 회귀를 감시한다.

---

## Step 4. AC 검증

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
[4/7] AC 검증 — Issue #$ARGUMENTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

`/ac-verifier $ARGUMENTS` 스킬을 호출한다.

브라우저에서 실제 앱을 조작하여 AC 충족 여부를 독립 검증한다. FAIL 항목이 있으면 사용자에게 보고되고, 사용자가 수정 여부를 결정한다.

AC 검증 결과에 FAIL이 있으면 컨테이너는 **중단**한다:

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
STOP [4/7] AC 검증 실패 — Issue #$ARGUMENTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
AC 미충족 항목이 있습니다.
수정 후 /tdd-loop $ARGUMENTS 를 다시 실행하세요.
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

---

## Step 5. TDD Refactor

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
[5/7] TDD Refactor — Issue #$ARGUMENTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

`/tdd-refactor $ARGUMENTS` 스킬을 호출한다.

테스트 통과 상태를 유지하면서 코드 구조를 개선한다. 변경마다 `npm test`를 실행하고, 깨지면 즉시 롤백한다.

---

## Step 6. Security Review

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
[6/7] Security Review — Issue #$ARGUMENTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

`/security-review $ARGUMENTS` 스킬을 호출한다.

tsc / npm audit / 보안 패턴을 점검하고 결과를 즉시수정/권장/무시로 분류한다. 사용자가 처리 방법을 선택한다.

---

## Step 7. PR 생성

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
[7/7] PR 생성 — Issue #$ARGUMENTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

`/create-pr` 스킬을 호출하되, `$BASE_BRANCH=$SPEC_BRANCH`를 전달하여 다음 사항을 보장한다:

- **커밋 메시지**: commitlint 통과 형식 (Conventional Commits)
- **PR base**: `$SPEC_BRANCH` (Step 0에서 기억한 스펙 브랜치, create-pr에 `$BASE_BRANCH`로 전달)
- **PR body**: `Closes #$ARGUMENTS` 포함
- PR 생성 성공 후, 이슈에 PR 링크 코멘트를 남긴다:
  ```bash
  gh issue comment $ARGUMENTS --body "PR: {PR_URL}"
  ```


## 실패 시 출력

어느 단계에서든 실패하면:

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
STOP [N/7] {단계 이름} 실패 — Issue #$ARGUMENTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
{실패 원인 요약}

수정 후 해당 단계부터 개별 스킬로 재실행하세요:
  /{스킬명} $ARGUMENTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

## 절대 금지

- **컨테이너가 스킬 내부 로직을 직접 수행하는 것** — 반드시 해당 스킬을 호출한다
- **"다음 단계 진행할까요?" 같은 추가 확인을 만드는 것** — 스킬이 끝나면 바로 다음으로 넘어간다
- **실패한 단계를 건너뛰는 것** — 실패 시 반드시 중단한다
- **Step 0 사전 점검 없이 스킬을 호출하는 것** — 환경이 준비되지 않으면 시작하지 않는다
