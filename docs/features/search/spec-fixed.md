# Search 기능 확정 요구사항

## 용어 정의

| 용어                     | 정의                                                      |
| ------------------------ | --------------------------------------------------------- |
| 검색어(query)            | 사용자가 검색 입력 필드에 입력한 텍스트                   |
| 필터링(filtering)        | 검색어와 일치하는 노트만 목록에 표시하는 동작             |
| 검색 대상(search target) | 검색어가 비교되는 노트 필드 — 제목(title)과 본문(content) |

## 1. Primary User

단일 사용자(개인). 현재 앱은 인증 없는 개인 노트 CRUD 앱이므로, 검색도 로컬 사용자가 자신의 노트를 찾는 용도로 한정한다.

## 2. 최소 동작 시나리오

1. **기본 검색**: 사용자가 검색 필드에 키워드를 입력하면, 제목 또는 본문에 해당 키워드가 포함된 노트만 사이드바에 표시된다.
2. **검색 초기화**: 검색 필드의 X 버튼을 누르거나 입력을 비우면, 전체 노트 목록으로 복원된다.
3. **검색 중 노트 선택**: 필터링된 목록에서 노트를 클릭하면 정상적으로 편집기에 표시된다.

## 3. 데이터 저장 방식

검색어는 서버에 저장하지 않는다. 클라이언트 사이드 필터링만 수행하며, 기존 `notes` 배열을 필터링해서 표시한다. 추가 API 엔드포인트 없음.

## 4. 경계 조건

- **빈 검색어**: 전체 노트를 표시한다 (검색 전 상태와 동일).
- **공백만 입력**: 빈 검색어와 동일하게 처리한다 (trim 적용).
- **특수문자**: 정규식이 아닌 단순 문자열 포함(includes) 매칭. 특수문자도 리터럴로 검색된다.
- **대소문자**: 무시한다 (case-insensitive).
- **노트 0건**: 검색 입력 필드 자체가 표시되지 않는다 (기존 "노트가 없습니다" 메시지 유지).
- **검색 결과 0건**: "검색 결과가 없습니다" 메시지 표시.

## 5. 에러 처리

클라이언트 사이드 필터링이므로 네트워크 에러가 발생하지 않는다. 기존 노트 로딩 에러 처리(`loading`, `error` 상태)는 그대로 유지하며, 검색 입력은 로딩/에러 상태에서는 표시하지 않는다.

## 6. 기존 UI 패턴과의 일관성

- 검색 입력 필드는 사이드바(NoteList) 상단에 배치한다.
- 디자인 시스템의 기존 색상(`text-foreground`, `text-muted-foreground`, `bg-card`, `border-border`)과 둥근 모서리(`rounded-xl`) 패턴을 따른다.
- 새 컴포넌트를 분리하지 않고 NoteList 내부에 검색 상태를 로컬로 관리한다.

## 7. 성능 제약

- 클라이언트 사이드 필터링이므로 노트 수백 개까지는 문제 없다.
- `useMemo`로 불필요한 재계산을 방지한다.
- 디바운스는 적용하지 않는다 — 로컬 필터링은 충분히 빠르다.

## 8. 향후 확장 가능성

- 태그(tag) 기능이 추가되면 검색 대상에 태그를 포함할 수 있다. 현재 필터링 로직이 `useMemo` 내부에 격리되어 있으므로 확장이 용이하다.
- 서버 사이드 검색(full-text search)은 현재 범위 밖이나, 필요 시 API 레이어에 검색 엔드포인트를 추가하고 Context에서 호출하는 형태로 전환 가능하다.
